Componentes Principales de la Arquitectura

🌐

HTTP Request / HTTP Response

Representa la petición web entrante enviada por el cliente (navegador, aplicación móvil o Postman) y la respuesta final que el servidor devuelve tras procesarla.

Entrada / Salida Global
🌉

DelegatingFilterProxy

Actúa como un puente entre el contenedor de servlets estándar (como Tomcat) y el contexto de Spring. Intercepta la petición HTTP y delega su control a los filtros manejados por Spring.

org.springframework.web.filter
🔗

Security Filter Chain

Es una cadena ordenada de filtros de seguridad por los que pasa la petición de forma secuencial. Cada filtro se encarga de una tarea específica (manejo de sesiones, extracción de credenciales, validación de tokens o protección CSRF).

FilterChainProxy / SecurityFilterChain
🎯

AuthenticationManager

Es el coordinador principal de la autenticación. Recibe las credenciales extraídas por los filtros y busca cuál de sus proveedores registrados (AuthenticationProvider) sabe cómo validarlas.

ProviderManager
🔑

AuthenticationProvider (1 y 2)

Son los módulos que ejecutan la lógica concreta de validación. Por ejemplo, uno puede encargarse de autenticar usuarios locales contra la base de datos y otro mediante LDAP o un servidor externo.

DaoAuthenticationProvider / OAuth2...
👤

UserDetailsService

Interfaz encargada únicamente de recuperar los datos del usuario (nombre, contraseña hasheada, roles) a partir del identificador (email o username) recibido.

loadUserByUsername()
🗄️

BD (Base de Datos)

El repositorio persistente donde residen las tablas con las credenciales, roles y permisos de los usuarios (PostgreSQL, MySQL, SQL Server, etc.).

SQL / NoSQL Storage
🔒

PasswordEncoder

Herramienta criptográfica que compara la contraseña en texto plano enviada por el usuario con el hash seguro guardado en la base de datos (usando algoritmos como BCrypt).

BCryptPasswordEncoder
🧠

SecurityContextHolder

Es la memoria local del hilo de ejecución actual donde queda almacenada la sesión del usuario una vez autenticado. Contiene al Principal (quién es el usuario) y sus Authorities (qué roles y permisos tiene).

ThreadLocal SecurityContext

Protección CSRF (Cross-Site Request Forgery)

CSRF es un ataque que engaña al navegador de un usuario autenticado para que ejecute acciones no deseadas en una aplicación web en la que dicho usuario confía.

⚠️ ¿Cómo funciona el ataque sin protección?

  • 1. Sesión Activa: Inicias sesión en tu aplicación bancaria o panel de administración; el navegador guarda tu cookie de sesión (JSESSIONID).
  • 2. Navegación Trampa: Sin cerrar sesión, visitas una web maliciosa o haces clic en un enlace sospechoso.
  • 3. Disparo Automático: La página atacante ejecuta un script invisible que dispara una petición hacia tu banco.
  • 4. Explotación: Como los navegadores adjuntan automáticamente las cookies del dominio destino, el servidor recibe la cookie válida y procesa la transferencia creyendo que fuiste tú.

🛡️ Protección CSRF en Spring Security

Garantiza que cada petición que cambie el estado de la aplicación (POST, PUT, DELETE, PATCH) provenga genuinamente de la interfaz de tu aplicación.

  • Generación del Token: El servidor genera un valor criptográfico aleatorio, único e impredecible (el token CSRF) asociado a la sesión del usuario.
  • Inclusión en el cliente: El servidor envía este token en la vista HTML (en un campo oculto del formulario o en una cookie legible como XSRF-TOKEN).
  • Envío obligatorio: Cuando el usuario envía una petición POST/PUT/DELETE, el cliente debe reenviar ese token en el cuerpo o en un encabezado HTTP (como X-XSRF-TOKEN).
  • Validación (CsrfFilter): Intercepta la petición entrante antes de que llegue a tus controladores. Si el token falta o no coincide, rechaza la petición con un 403 Forbidden.

⚖️ ¿Cuándo debe habilitarse o deshabilitarse?

✅ HABILITADA (Por defecto en Spring Security)

Indispensable cuando la aplicación utiliza autenticación basada en sesiones y cookies y renderiza vistas en el servidor (ej. Thymeleaf, JSP o frontends que comparten cookies de sesión).

❌ DESHABILITADA (http.csrf(csrf -> csrf.disable()))

Es común desactivarla únicamente en APIs REST Stateless que utilizan tokens en cabeceras (como JWT mediante Authorization: Bearer <token>) y que no almacenan credenciales ni sesiones en cookies del navegador, ya que los navegadores no adjuntan cabeceras Authorization automáticamente en peticiones cruzadas.

Estrategias de AuthenticationProvider

El concepto de AuthenticationProvider en Spring Security está pensado justamente para que una misma aplicación pueda validar credenciales de múltiples fuentes y tecnologías.

┌──► [AuthenticationProvider 1] (DaoAuthenticationProvider / Base de Datos) [AuthenticationManager] ─┤ └──► [AuthenticationProvider 2] (OAuth2LoginAuthenticationProvider / Google, Meta)

DaoAuthenticationProvider (El estándar de Spring)

Cómo funciona: Toma el usuario y contraseña ingresados, llama a tu UserDetailsService para consultar la base de datos (PostgreSQL, MySQL, SQL Server, etc.) y usa PasswordEncoder (BCrypt) para verificar el hash.

Caso de uso: Tu formulario clásico de login propio (/login) con correo y contraseña.

LdapAuthenticationProvider

Cómo funciona: Valida las credenciales contra un servidor corporativo de Active Directory o LDAP.

Caso de uso: Sistemas internos o intranets de empresas donde los empleados usan su usuario corporativo de red para ingresar.

OAuth2LoginAuthenticationProvider / OidcAuthorizationCodeAuthenticationProvider

Cómo funciona: En lugar de pedir la contraseña al usuario en tu sitio, redirige al usuario a la página de autenticación del tercero (Google, Meta, Apple, GitHub). Cuando el tercero devuelve un código de autorización temporal, este proveedor lo intercambia por un ID Token y un Access Token, validando la firma criptográfica del proveedor.

Google (OpenID Connect)

Valida la identidad del usuario contra las cuentas de Google (accounts.google.com).

Meta / Facebook

Obtiene el perfil básico y el ID de usuario desde las APIs de Meta Graph.

GitHub

Típico en herramientas de desarrollo o plataformas técnicas.

JwtAuthenticationProvider

Cómo funciona: Recibe un token JWT enviado en la cabecera Authorization: Bearer <token>, comprueba su firma digital (con clave pública/secreta), verifica que no esté expirado y extrae los claims (roles, sub, permisos).

Caso de uso: Microservicios, APIs REST consumidas por React, Next.js, Flutter o móviles.

Servidores de Identidad Dedicados

Herramientas: Keycloak, Auth0, Okta, Firebase Auth.

Delegan la validación de tokens a un servidor de identidad centralizado que orquesta la seguridad de toda la empresa.

¿Cómo interactúan en el diagrama?

Fíjate en las dos flechas que salen de AuthenticationManager: Si el usuario envía usuario y contraseña, delega la validación al Provider 1 (interno). Si el usuario llega desde el flujo de Google o Meta, delega la validación al Provider 2 (OAuth2). Si cualquiera de los dos valida con éxito al usuario, genera el objeto Authentication y lo deposita en el SecurityContextHolder, permitiendo unificar la sesión independientemente del método de entrada.

¿Qué es LDAP (Lightweight Directory Access Protocol)?

LDAP significa Lightweight Directory Access Protocol (Protocolo Ligero de Acceso a Directorios). Es un protocolo de red estándar que se utiliza para buscar, consultar y modificar información sobre usuarios, equipos y permisos organizados de forma centralizada en un servicio de directorio (como Microsoft Active Directory u OpenLDAP).

¿Para qué sirve?

📂 Directorio Único

La información de los empleados (nombre, correo, departamento, contraseña y permisos) se almacena en un único lugar en forma de árbol jerárquico.

🔑 Autenticación Centralizada (SSO)

En lugar de que cada aplicación gestione su propia base de datos de usuarios, le pregunta al servidor LDAP: "¿Este usuario existe y su contraseña es correcta?".

⚡ Búsqueda Rápida

Está diseñado y optimizado específicamente para operaciones de lectura y búsqueda masivas y rápidas, más que para escrituras frecuentes.

🏢 Ejemplo Práctico

Imagina que una empresa contrata a un empleado llamado Carlos:

  1. El administrador de sistemas da de alta a Carlos una sola vez en el servidor de directorio central (ej. Active Directory).
  2. Cuando Carlos quiere ingresar a la VPN, al correo institucional, al panel interno en Spring Boot o a una computadora de la oficina, introduce su mismo usuario y contraseña.
  3. Cada uno de esos sistemas (mediante un cliente o proveedor LDAP como LdapAuthenticationProvider en Spring Security) consulta al servidor LDAP para verificar las credenciales sin necesidad de duplicar los datos de Carlos en cada base de datos.
